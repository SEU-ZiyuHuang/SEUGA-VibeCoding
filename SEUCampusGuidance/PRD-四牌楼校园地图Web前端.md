## 1. 产品概述

### 1.1 一句话定位

这是一个把校园地图、生活指南、学校官方资料、办事流程和智能问答放在同一个入口的校园服务产品。用户可以直接找地点、查资料，也可以用自然语言提问，由 Agent 带他回到可信的原文、具体的地点或下一步操作。

### 1.2 当前要解决的问题

校园信息散落在地图、学校各部门网站、公众号文章、办事系统和历年指南里。用户往往不知道应该搜什么、到哪里找，也判断不了看到的信息是否还有效。本产品先解决四类高频问题：

1. **地点在哪里**：建筑、食堂、宿舍、打印点、医院、交通站点等，能查、能看、能找到。
2. **校园生活怎么办**：把宿舍、学习、餐饮、交通和周边服务整理成可检索的电子指南。
3. **学校事务如何办理**：把材料、步骤、窗口、线上入口和注意事项放在一起。
4. **复杂问题如何继续问**：Agent 理解用户意图，给出有来源、能继续操作的答案，而不是只生成一段文字。

### 1.3 用户与核心任务

主要用户是在校学生、新生、访客和内容维护人员。公开端优先支持以下任务链：

- 找地点 → 看详情 → 查看附近服务或规划步行路线；
- 查指南 → 查看完整记录 → 回到对应的地图地点；
- 查办事流程 → 核对材料和步骤 → 查看窗口或继续问 Agent；
- 查学校资料 → 确认适用对象和时效 → 打开官网原文或带着资料问 Agent。

### 1.4 产品边界

- 公开地图、地点详情和电子指南目前只覆盖四牌楼校区。
- 知识中心收录的是多个校区、面向不同人群的学校官网公开资料，不等于六个校区都有地图。
- 独立的校园 Agent 已经能做六校区知识问答；四牌楼公开端里内嵌的是一个轻量问答入口，两者能力还没有统一。
- 本产品提供信息查询、导航和官方办理入口，最终仍以学校正式通知和业务系统为准。
- 开放时间、班次、服务状态大多是定期整理的静态信息；除非明确标了采集时间，否则不要当成实时数据。

## 2. 当前产品结构

产品不是“地图旁边放一个聊天框”，而是三个互相连接的工作区：

| 工作区 | 当前职责 | 当前数据范围 |
| --- | --- | --- |
| 公开端 | 地图、搜索、地点详情、路线、电子指南、办事流程、知识中心和 Agent 入口 | 四牌楼地点与 2025.08 版指南；学校官网公开资料 |
| 内容管理端 | 维护地点与办事流程，保存草稿并统一发布 | 地点覆盖内容、后台新增内容和流程内容 |
| 校园 Agent | 页面内轻量入口回答问题并返回相关地点；独立 Agent 承担六校区深度问答 | 两套入口共享校园指南知识，但上下文、来源和地图返回能力还没统一；都还没有接入实时校方数据和个人数据 |

前端的设计思路是“先看概览、再看细节”：地图上只显示和当前任务有关的标记；列表里给出名称、类别和位置摘要；点进详情再展开开放时间、设施、指南记录、来源、路线和下一步操作。以后数据再多，也保持这个节奏——信息可以更丰富，但不要把地图铺满标签。

### 3.3 数据与运行基础

- 地图使用腾讯地图 JavaScript 和步行路线服务；密钥放在服务端环境配置里，并限制了使用域名。
- 地图地点、人工点位、电子指南、原版图册、办事流程和知识资料都有各自独立的数据文件。
- 后台发布的内容与原始指南分开存储，可以覆盖旧条目，也可以新增条目。
- 在线 Agent 和本地规则查询都能返回四牌楼地点 ID；前端会对返回的地点聚焦和高亮。
- 知识中心展示资料来源、发布部门、发布日期、适用人群、适用校区和原文入口，并提示摘要不能替代正式文件。

## 4. 当前问题与建设原则

### 4.1 当前最需要解决的问题

1. **信息不少，但大多是静态的**：有比较完整的静态指南，但缺教室、座位、开放状态、临时关闭、施工、校车这类动态数据。
2. **数据之间还没有打通**：同一个地点在地图、指南、办事流程、知识资料和 Agent 里没有统一的对象 ID、来源和更新时间。
3. **Agent 还像一个独立的问答框**：能回答、能高亮地点，但还不能稳定理解“这里”“这份资料”“刚才那个流程”，也不能输出可验证的结构化结果和安全的前端动作。
4. **内容运营没有闭环**：后台能编辑和发布，但缺责任人、复核时间、过期提醒、审批、发布历史、回滚和用户纠错处理。
5. **覆盖范围有限**：四牌楼还缺建筑边界、入口、楼层、房间、无障碍设施这类高密度空间信息；其他校区的地图还没开始做。

### 4.2 提高信息密度的原则

信息密度不是“页面字更多”，而是让用户少跳页面、少猜关键词，在一个任务上下文里拿到足够的信息。

- **地图层**：缩放小时显示校区、片区、出入口和主要设施；放大后再显示楼栋、服务点、入口和室内空间；重叠的标记自动聚合。
- **列表层**：每条至少给出名称、类别、距离或位置、开放状态，以及一条最有用的服务标签。
- **详情层**：在同一张卡里组织位置、时间、设施、适用人群、关联流程、官方入口、来源和更新时间。
- **动态层**：常规开放时间和“现在是否开放”分开显示；动态数据必须带采集时间，过期后自动降级为“状态未知”。
- **可信层**：每条重要事实都带来源类型、责任部门和时间口径。学校官网、校方系统、校园指南和人工维护的信息，不能混成同一种可信度。
- **操作层**：详情不是信息终点，应该直接给出附近、路线、查看流程、打开原文、继续问 Agent 等下一步。

## 5. 将要实现的功能

### 5.1 近期：补齐正式运营能力

近期目标是让现有产品可信、可维护、能稳定使用，而不是急着加更多入口。

| 需求 | 完成后的体验 | 验收标准 |
| --- | --- | --- |
| 统一对象与来源字段 | 地图、指南、流程、资料和 Agent 使用同一套地点／服务／资料 ID；详情统一显示来源和更新时间 | 同一对象跨模块跳转不丢上下文；主流程不再靠名称猜测关联；重要信息都有 `source`、`verifiedAt` 或相应的时间字段 |
| 补全高频办事流程 | 覆盖新生报到、校园卡、校园网、住宿、打印、图书馆、教务、研究生事务、户政、医疗和常用证明 | 每条流程写明适用对象、材料、步骤、办理入口、地点、责任部门、核验时间和失效条件 |
| 知识中心正式化 | 去掉演示链接；建立来源核验、过期提醒和历史归档 | 所有当前资料都能打开有效的官方原文；链接到期或异常时自动标记并进入复核队列 |
| 用户纠错闭环 | 用户可在地点、流程和资料处报告错误，并看到受理状态 | 反馈包含对象 ID、问题类型和页面上下文；后台能受理、处理、回复并留痕 |
| 后台可靠发布 | 支持账号角色、审核、版本差异、发布历史和一键回滚 | 编辑与发布权限分离；每次发布记录操作者、时间和变更摘要；失败不会覆盖上一个可用版本 |
| 运行监控 | 监控地图、路线、Agent、内容读取和发布接口 | 核心接口失败能定位到具体请求；用户看到明确的降级提示；不把缓存或旧数据伪装成实时结果 |
| 移动端与可访问性验收 | 手机、键盘和屏幕阅读器能完成核心任务 | 在主流手机宽度完成搜索、选点、查看详情、路线和提问；关键控件有名称、焦点和状态反馈 |

### 5.2 下一阶段：提高地图密度并统一 Agent 交互

#### A. 地图与空间能力

- 建立“校区—片区—建筑—楼层—房间—服务点”的空间层级，补充建筑边界、入口、门牌、楼层、无障碍通道、电梯、卫生间、饮水、充电、打印、AED 等信息。
- 根据缩放、当前时间、用户任务和筛选条件控制显示密度；提供标记聚合、片区概览和室内楼层切换。
- 把“常规时间、临时调整、当前状态”分开建模；实时接口不可用时保留常规信息，并明确标注“当前状态未知”。
- 支持多条件任务查询，例如“现在开放、离我 500 米内、有插座的自习空间”，结果同时出现在列表和地图上。

验收标准：从校区概览到具体服务点不超过三次主要操作；重叠标记不会遮挡核心地点；每个动态状态都显示更新时间或非实时提示。

#### B. Agent 与前端统一

目前公开端的 Agent 和独立的六校区 Agent 能力不同：前者能返回四牌楼地点，但缺多轮上下文和结构化来源；后者有六校区识别、多轮对话和来源展示，但还不能稳定返回地图对象。下一阶段应统一成同一套对话和结构化结果协议。

前端把用户当前可见的上下文提供给 Agent：校区、选中地点、地图范围、筛选条件、知识资料 ID、办事流程 ID，以及本次会话历史。这样用户才能自然地问“这里几点关门”“这份通知适用于研究生吗”“从我这里怎么走”。

Agent 的回答按需由四部分组成：

1. 简短结论；
2. 地点、资料、流程或路线卡片；
3. 来源、责任部门和更新时间；
4. 可执行的下一步按钮。

前端动作只允许白名单内的：高亮或聚焦地点、应用筛选、打开地点详情、打开资料、打开流程、发起路线预览。无效的对象 ID 或白名单外的动作不执行。高亮和筛选可以自动执行，但页面要显示“Agent 已应用的操作”并允许撤销；定位、外部链接和正式办理仍由用户主动触发。

这一阶段的验收要求：

- “这里”“附近”“这份资料”“刚才的流程”等追问能承接正确的对象；不确定时先问清楚，不静默猜测。
- 易变信息必须展示更新时间；每个事实性回答至少给出一个可核对的来源。
- Agent 能一次返回多个地点，并在列表和地图上一致展示，而不是只定位第一个。
- 在线服务超时或来源过期时明确降级，保留用户已查看的页面上下文。
- Agent 不得修改后台内容，也不得替用户提交学校业务。

### 5.3 长期：多校区、动态数据与校园服务联动

- 按统一的空间和内容模型扩展到九龙湖、丁家桥、苏州、江北、无锡等校区，先做高频地点和服务，再补室内空间。
- 接入教室与学习空间、图书馆座位、场馆与窗口状态、校车、停水停电、施工封路等动态数据。
- 接入学校统一身份认证后，在用户授权范围内查询个人课表、预约和业务进度，并把用户带回官方系统完成办理。
- 预约、报修、取消等写操作采用“操作预览—用户确认—官方系统返回结果”三步；支付和高风险事项不由 Agent 自动完成。

## 6. 与学校网络与信息中心的合作需求

网络与信息中心适合作为统一认证、接口接入、主数据和平台治理的合作方，但教务处、总务处、图书馆、保卫处、校医院等业务部门仍应对各自数据的准确性和更新负责。合作的目标不是一次性导出表格，而是建立可持续的数据责任、接口和失效机制。

### 6.1 优先合作事项

| 优先级 | 需要的支持 | 主要用途 | 数据责任与时效 | 接口不可用时 |
| --- | --- | --- | --- | --- |
| P0 | 统一校区、建筑、房间、入口和服务主数据编码 | 让地图、后台、知识库和 Agent 使用同一套对象 ID | 网信中心协调主数据；空间变更即更新，至少每季度复核 | 沿用现有 ID；匹配不上的对象只展示文字，不触发地图动作 |
| P0 | 统一身份认证、角色权限、API 网关和访问审计 | 后台多人协作，以及以后安全查询个人数据 | 网信中心提供；认证与审计实时生效 | 公开功能继续使用；关闭个人查询和管理写操作 |
| P0 | 官方办事服务目录和系统深链接 | 补全“去哪办、准备什么、线上入口在哪” | 网信中心协调各责任部门；变更即更新，至少每日检查 | 展示人工核验的流程和官方原文，标明核验时间 |
| P0 | 建筑边界、入口、楼层、房间、无障碍和应急设施数据 | 提高地图空间密度，支持室内和无障碍查询 | 总务、基建、保卫等部门负责；变更即更新，至少季度复核 | 保留已有 POI，不提供未经验证的室内路线 |
| P1 | 场所开放时间、临时关闭和服务状态 | 回答“现在能不能用”，减少到场后落空 | 图书馆、总务、体育、医院等部门负责；固定数据每日同步，临时变化尽快推送 | 只显示常规时间，并标注“当前状态未知” |
| P1 | 空教室、学习空间、图书馆座位与研讨室 | 支持按时间、容量和设施找可用空间 | 教务处、图书馆负责；动态状态建议 1—15 分钟更新 | 跳转官方查询或预约入口，不声称当前空闲 |
| P1 | 校车线路、时刻和运行状态 | 支持跨校区出行和换乘建议 | 交通管理部门负责；时刻变更即更新，车辆位置建议 30—60 秒 | 降级为带生效日期的静态时刻表 |
| P1 | 停水停电、系统维护、施工封路和紧急通知 | 在地图详情和 Agent 回答中提示影响 | 总务、保卫、网信等部门负责；事件发生时推送，过期自动撤下 | 展示官方通知入口，不推测恢复时间 |
| P2 | 本人课表、预约和业务进度查询 | 登录后提供个性化提醒和办理入口 | 各业务系统负责；按用户授权实时查询 | 只回答通用流程并跳转原系统 |

所有接入数据至少包含：稳定 ID、名称、来源部门、更新时间、有效期、访问级别、版本和当前状态。动态数据还要有采集时间和失效阈值；没有这些字段，就不能在页面或 Agent 回答里标为“实时”。

### 6.2 数据访问与安全边界

- **公开数据**（校园空间、开放服务、公开通知、办事指南）可以进入前端搜索和 Agent 检索。
- **登录后数据**只在用户主动授权后即时查询，不进入公共知识库，不做超出本次任务所需的长期缓存。
- 以下数据不接入 Agent：成绩、处分、医疗记录、校园卡消费明细、门禁记录、人脸与视频、人员名册、Wi-Fi 定位轨迹、银行卡信息、密码和长期令牌。
- 用户精确位置仅在浏览器授权后用于附近和路线任务，不保存位置轨迹。
- 个人数据、身份令牌和敏感字段不得进入模型提示词、公共知识库或普通运行日志。
- 涉及正式办理时优先跳转校方系统；本产品不复制源系统数据，也不绕过原有权限和审批。

## 7. 质量要求、路线图与验收

### 7.1 统一质量底线

| 方面 | 要求 |
| --- | --- |
| 准确性 | 地点、流程和资料都有责任来源；旧数据不得以“当前”的口吻展示；医疗、治安和消防问题优先给出 120、110、119 及校内官方求助入口 |
| 时效性 | 区分 `publishedAt`（发布日期）、`verifiedAt`（人工核验时间）、`observedAt`（动态采集时间）和 `validUntil`（有效期） |
| 稳定性 | 地图、路线、Agent 或动态接口失败时，给出明确提示和可用的替代入口；不能显示假成功 |
| 性能 | 首屏优先加载基本地图、搜索和地点；指南图片、知识详情和非当前图层按需加载；动态数据不得阻塞静态内容浏览 |
| 安全与隐私 | 密钥只在服务端配置；管理和个人接口鉴权、限流、记录必要审计；按最小权限处理身份、位置和个人数据 |
| 可访问性 | 核心流程可用键盘完成；控件、弹窗、加载、错误和选中状态可被辅助技术识别；颜色不是唯一的状态提示 |
| 可维护性 | 每种对象有稳定 ID 和明确负责人；内容更新、审核、发布、回滚和过期处理都有记录 |

### 7.2 分阶段交付

| 阶段 | 交付结果 | 完成判定 |
| --- | --- | --- |
| M0：上线基线（当前） | 四牌楼地图、指南、办事服务、知识中心、轻量 Agent 和受保护的内容后台 | 第 3 章所列能力保持可用；后台发布链路补做一次管理员端到端验收 |
| M1：正式运营 | 统一 ID 与来源、补全高频流程、知识核验、用户纠错、后台账号审核与版本回滚、运行监控 | 内容可追责、可复核、可安全回滚；当前资料没有演示链接；异常有明确降级 |
| M2：地图与 Agent 融合 | 高密度空间数据、组合筛选、结构化上下文、来源卡片和白名单前端动作 | 用户能从自然语言问题完成“找到—看懂—到达／办理入口”的闭环，且每一步可核验和撤销 |
| M3：校方数据合作 | 统一认证、数据网关、动态空间与服务数据，逐步扩展多校区和个人授权查询 | 数据责任、更新频率、失效策略和权限经过校方确认；动态数据不被缓存冒充实时 |

### 7.3 主要依赖与风险

- **校方数据协调**：网信中心不一定持有所有业务数据，需要明确牵头部门、数据责任人和更新承诺；没有责任人的数据，宁可标为人工核验，也不要包装成自动同步。
- **第三方服务**：腾讯地图、模型服务和内容存储可能出现额度、网络或配置故障，必须保留静态信息和官方入口等降级路径。
- **内容过期**：校园服务变化频繁，应通过有效期、异常链接检测、定期复核和用户反馈共同发现问题。
- **Agent 误答或误操作**：答案必须带来源；实时信息通过受控接口查询；界面动作走白名单；写操作保留用户确认和校方系统最终结果。
- **多校区混淆**：所有地点、资料和回答都要明确校区上下文；无法判断时先问用户，不自动猜测。

### 7.4 本版不承诺的内容

- 不承诺尚未接入的数据是实时数据。
- 不承诺页面内 Agent 已具备完整的多轮上下文、结构化来源和校务办理能力。
- 不承诺内容管理端已具备多人协作、审批、审计和版本回滚。
- 在校方授权和安全评审之前，不接入个人敏感数据，也不自动执行正式业务。

| 术语 | 含义 |
